# はじめに

ローカルの作業ディレクトリ・外付けHDD・NASの共有フォルダなど、複数の場所に散らばったフォルダを行き来する作業がエクスプローラーだと面倒でした。場所ごとにウィンドウを開き直し、探し物のたびにフォルダごとに検索をかけ直し、NAS上のフォルダは開くたびに待たされる。

そこで、**任意のルートフォルダを複数登録して1つのツリーとして横断ブラウズ・検索できる**アプリ **ParallelScope** を作りました。WPF（.NET 10）+ ローカルSQLiteキャッシュ構成です。

- リポジトリ: <https://github.com/msmsrep/ParallelScope>
- 使い方ガイド: <https://msmsrep.github.io/ParallelScope/index.ja.html>

この記事では、実装で効果が大きかったポイントだけに絞って書きます。

# 1. 表示は「キャッシュ即時 → 実体で上書き」の2段構え

フォルダを開いた瞬間にファイルシステムを列挙すると、NASや大量ファイルのフォルダで固まります。そこで **表示は必ずSQLiteキャッシュから始める** 構成にしました。

1. キャッシュから直下エントリを読んで即表示
2. バックグラウンドでファイルシステムを読み直し、一覧とキャッシュを置き換え
3. キャッシュから集計した「子フォルダの合計サイズ」を後追いで反映

体感は「開いた瞬間に出る → 少し遅れてサイズ欄が埋まる」になります。

## 連続リクエストの統合

この3つはどれも「実行中に次のリクエストが来る」のが常態です（ツリー連打、検索欄へのタイプ）。各所に `_isRunning` と `_pendingRequest` のフラグ組を書いていたので、汎用クラスへ切り出しました。

```csharp
/// <summary>
/// 連続したリクエストを1つに統合し、非同期ハンドラを直列に実行する汎用キュー。
/// 実行中に新しいリクエストが来た場合は最新のものだけを保持し、完了後に処理する
/// （途中のリクエストは破棄される = 最新状態のみが反映される）。
/// </summary>
public sealed class SingleFlightCoalescer<TRequest>
{
    public void Request(TRequest request)
    {
        lock (_gate)
        {
            _pendingRequest = request;
            _hasPendingRequest = true;

            if (_isRunning)
            {
                return;   // 実行中なら「最新リクエストの上書き」だけして即リターン
            }

            _isRunning = true;
        }

        _ = RunAsync();
    }
}
```

ポイントは **中間のリクエストを捨てる** こと。UIの表示更新は最新状態さえ反映されればよく、全部処理するのは無駄です。1つ用意しておくと一覧更新・検索・フォルダサイズ・フラット表示で使い回せて、非同期まわりのバグがまとめて消えました。

# 2. スキャンは「ウェーブ単位の並列列挙」

キャッシュを最新に保つため定期的にフルスキャンします。素直な再帰列挙は **ローカルSSDでは十分速いのにNASでは絶望的に遅い**。1ディレクトリの列挙がラウンドトリップ数回分になるので、直列だと「レイテンシ × フォルダ数」が積み上がります。

対策はディレクトリを**ウェーブ（束）単位で取り出して並列に列挙**すること。

```csharp
// 全コアを使うとバックグラウンドのフルスキャン中にスレッドプールが飽和し、
// UIの応答（ツリー選択時のキャッシュ読み込み等のTask.Run）が待たされる。
// 列挙はほぼI/Oバウンド（特にNASではラウンドトリップのレイテンシが支配的）なので、
// ディレクトリ単位で並列化しつつ同時実行数は絞る。
private static readonly ParallelOptions DirectoryEnumerationParallelOptions = new()
{
    MaxDegreeOfParallelism = Math.Max(2, Environment.ProcessorCount / 2)
};

// ウェーブは並列度より大きめに取り、列挙の速いディレクトリと遅いディレクトリの偏りを均す
var waveCapacity = DirectoryEnumerationParallelOptions.MaxDegreeOfParallelism * 4;
```

設計のキモは **並列にするのは列挙だけ** という切り分けです。バッチ書き込み・訪問済みセットの管理・失敗の分類はウェーブ間の逐次パートで行うので、共有状態のロックが要りません。

## 「列挙に失敗した」を空フォルダと区別する

NAS相手では **スキャン中のネットワーク切断** が普通に起こります。ここで例外を握りつぶして空リストを返すと、既存キャッシュが空で上書きされ「フォルダの中身が全部消えた」ように見えます。今は失敗の種類で扱いを分けています。

| 状況 | 判定 | 扱い |
| --- | --- | --- |
| 列挙が例外、フォルダ自体は見える | 一時的なI/Oエラー | キャッシュを書き換えず、そのルートを**未完走**扱い（走査は継続） |
| 列挙が例外、ルートごと見えない | ネットワーク切断 | そのルートを打ち切り、未完走扱い |
| 列挙が例外、フォルダだけ消えた | 直前に削除された | 通常の残骸掃除に任せる |

そして **完走したルートについてだけ**「訪問しなかった親パス＝削除済み」とみなして残骸行を消します。未完走のルートを掃除対象に入れると、一時的に見えなかっただけのフォルダのキャッシュを削ってしまいます。

# 3. SQLite / EF Coreのチューニング

数十万〜数百万行を「書きながら読む」ので、設定を詰める価値がありました。

**`Cache=Shared` を付けない。** 共有キャッシュは接続間でテーブルロックを共有するため、WALの「書き込み中でも読み取り可能」という利点が消えます。付けていた頃はフルスキャン中のフォルダ移動が引っかかっていました。

**接続単位のPRAGMAはインターセプターで毎回適用する。** `journal_mode` はDBファイル側に永続化されますが、`synchronous` や `cache_size` は接続単位です。起動時の1接続にだけ適用していたころは、プールに接続が増えると既定値のまま動く不整合がありました。

```csharp
// 接続オープン時に、接続単位でしか効かないPRAGMAを毎回適用するインターセプター。
// PRAGMAの再適用はI/Oを伴わず数マイクロ秒で済む。
cmd.CommandText = @"
    PRAGMA synchronous = NORMAL;
    PRAGMA cache_size = -16000;
    PRAGMA temp_store = MEMORY;
    -- チェックポイント時にWALファイルをこのサイズまで切り詰める（フルスキャンでの肥大対策）
    PRAGMA journal_size_limit = 67108864;
";
```

**無変化なら書かない。** フルスキャンでも実際に中身が変わるフォルダはごく一部です。100フォルダごとのバッチ書き込みで、キャッシュ済み内容と比較して**差分があった親パスだけ** DELETE + INSERT しています。書き込み量とWALの膨張が桁で変わりました。

**インデックスは実測で削る。** 初期は `(ParentPath, Name)` / `Name` / `(IsFolder, Name)` を張っていましたが、どのクエリの実行計画にも使われず**パス文字列の重複保存でDBだけが肥大化**していました。今残しているのは `ParentPath`、重複行防止のための `FullPath` UNIQUE、検索・All Filesモード用の `(IsFolder, FullPath)` だけです。

# 4. インクリメンタルサーチはキャッシュだけで完結させる

検索欄は `UpdateSourceTrigger=PropertyChanged` でバインドし、1文字ごとにリクエストを投げます（検索ボタンもEnter起動もなし）。

- **ライブのファイルシステムに触らない。** 切断中のNASへの `Directory.Exists` は1キー入力ごとにUIスレッドを数秒〜数十秒ブロックしえます。
- **結果が届くまで表示中の一覧を消さない。** 入力のたびに空にするとちらつきます。
- **`lower(Name)` をやめて `LIKE` にする。** SQLiteの `LIKE` はASCIIの大文字小文字をもともと区別しない（`lower()` もASCIIしか畳まない）ので、行ごとの文字列生成なしで同じ判定になります。エスケープ文字はパス区切りの `\` と衝突しない `~` を使用。
- **`List` にせず `yield` で1件ずつ返す。** 検索語1文字だと数十万件ヒットします。中間リストを持つとピークメモリがほぼ倍増します。
- **遅れて返った結果は捨てる。** `Interlocked.Increment` したバージョンをリクエストに持たせ、UIスレッドで最新か確認してから反映します。

```csharp
var namePattern = "%" + EscapeLikePattern(nameQuery) + "%";

var rows = db.FileSystemEntries
    .AsNoTracking()
    .Where(x => x.FullPath.StartsWith(rootWithSeparator)
             && EF.Functions.Like(x.Name, namePattern, "~"))
```

# 5. 数十万件を `ObservableCollection` で捌く

配下の全ファイルをフラット表示する「All Files」モードでは、コレクションの中身が数万〜数十万件規模で入れ替わります。1件ずつ `Add`/`Remove` すると件数分の `CollectionChanged` が飛び（`Remove` は1件ごとに線形探索も走る）、UIスレッドが数秒ブロックされます。

そこで**差分件数で戦略を切り替え**ました。

- 差分が少ない（200件以下）: 追加/削除/更新を個別に適用し、既存行の再描画を避ける
- 差分が多い: `ObservableCollection` ごと差し替えて再バインド1回で済ませる（DataGridの行仮想化により生成されるのは可視行だけ）

差し替える場合も**既存アイテムのインスタンスは使い回します**（後追いで埋めたサイズ表示などを保つため）。同一性判定は `FullPath` ではなく `(Location, Name)` のタプル。`FullPath` は都度生成のプロパティなので、キーにすると差分計算のたびに全件分の文字列生成が走ります。

さらに5万件を超える入れ替えの後は、静止してから1回だけGCを予約しています。数十万件規模ではGen2/LOHに旧一覧が残り、ワーキングセットが積み上がったままになるためです。`GC.Collect()` は書きたくないコードですが、「タスクマネージャーで見たメモリ」が評価に直結するデスクトップアプリでは条件付きで割り切りました。

# おわりに

効果が大きかった順に並べるとこうなります。

1. **表示をキャッシュから始める**（体感速度がすべて変わる）
2. **連続リクエストを1クラスに統合する**（非同期まわりのバグがまとめて消える）
3. **並列化するのは副作用のないI/Oだけ**（並行バグの余地を減らす）
4. **失敗を「空」と区別する**（NAS相手ではデータ破壊に直結する）
5. **インデックスとPRAGMAは実測で削る**（付け足すより外すほうが効くことがある）

ソースは全部公開しているので、WPF + SQLiteでローカルキャッシュを持つアプリを作る人の参考になれば嬉しいです。
